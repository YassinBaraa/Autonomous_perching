Branch Detection Pipeline

The branch detection module of the perching UAV, as it runs on the Raspberry Pi 5 with the Hailo-8: image acquisition, YOLOv8m-seg inference, output decoding, multi-object tracking, geometric post-processing, the selection of the perch point handed to the IBVS tracker, the branch width sent with it as the packet size, and the overlay video drawn after each flight. Each stage links to its source.

All images are frame 230 of the 2026-10-13 18:11 flight, processed by the code described here. Timings are from the Raspberry Pi 5 with the Hailo-8 on PCIe Gen 2 ×1. Sections 0–6 describe detection_pipeline edf093d together with the fixes listed under Issues, committed since in 9bc1357 and 4d24c6b; their source links point to edf093d. Sections 7 and 8 link to ibvs 24aebb5 and Autonomous_perching 2d63592; their images are from the 2026-10-14 12:00 flight.

0 · OVERVIEW

Data flow

Summary Each camera frame is letterboxed to 640×640 and passed to a YOLOv8m-seg instance-segmentation network on the Hailo-8. The decoded detections (box, confidence, mask) are associated across frames by ByteTrack. The masks are merged, distance-transformed and skeletonised, and one perch point per branch is chosen on the skeleton under geometric constraints (orientation, distance to the branch tips, distance to crossings). The best point is handed to the IBVS tracker, which locks on it and continues with KLT optical flow.

DetectionPipeline.run() drives the chain: for each frame it calls the detector, the tracker and the post-processing stages, then yields the context. pipeline_factory.py assembles the components for the UAV.

Operating modes

Detection runs only while no target is locked (searching, or re-acquisition after a loss); it sustains about 6 Hz. After the lock, IBVSPipeline reads frames directly from the camera and tracks the point with KLT at about 27 Hz; the detection chain is idle.

1 · ACQUISITION

Image acquisition

DSJSource opens the DSJ-3079-HE USB camera through V4L2 and requests MJPG at 1280×720, 30 fps. The camera offers no square mode (MJPG: 640×480, 800×600, 1280×720, 1600×1200 and larger), so the 640×640 network input is produced in software (§2).

  • Buffer depth 1. The detection chain is slower than the camera. With the default V4L2 queue, stale frames accumulated and the transmitted point lagged by up to 20 s in an early test. With a single buffer, every read returns the most recent frame.
  • Grab timestamp. read() records time.monotonic() immediately after the grab. The UDP packet field age is the difference between send time and this timestamp (median 23 ms in flight).
  • Exposure and focus are automatic (aperture-priority exposure, continuous autofocus). This affects motion blur; see Issues.

2 · INFERENCE

Network inference on the Hailo-8

Summary YOLOv8m-seg (27.2 M parameters, 104.7 GFLOPs at 640², one class), compiled to a three-context HEF. Input: 640×640×3 uint8 RGB. Output: ten quantised tensors on three detection scales plus one set of prototype masks. Hardware latency 54 ms (hailortcli benchmark: 13.5 FPS); measured inference call in the pipeline: 52 ms.

Model

model/yolov8_segmentation.hef is YOLOv8m-seg compiled for the Hailo-8, with a single class (branch). It is an instance-segmentation model: every detection has a box, a confidence and a pixel mask. The network does not fit the chip's on-chip memory in one piece; the HEF has three contexts that the chip loads in turn on every inference, which bounds the throughput. The .pt files in the same directory are training checkpoints of other models (YOLO26 variants) and are not used on the UAV.

HailoSegDetector.__init__ creates the VDevice, configures the model and binds one output buffer per tensor. Only one process can hold the device, so an offline test that holds the Hailo blocks the flight software.

Input preparation: letterbox

The 1280×720 BGR frame is scaled by s = min(640/1280, 640/720) = 0.5 to 640×360, converted to RGB and padded with grey (114) by 140 rows above and below. This preserves the aspect ratio, as in YOLOv8 training. Until now the frame was resized to 640×640 directly, which scales x by 0.5 and y by 0.89 and distorts all shapes; §V quantifies the cost of that.

x_input = s · x_frame + pad_x s = 0.5, pad_x = 0 y_input = s · y_frame + pad_y pad_y = 140

Architecture. A CSP backbone extracts features at strides 8, 16 and 32; a PAN neck fuses them; three decoupled heads predict class score, box distribution and mask coefficients on the three feature grids; a prototype branch produces 32 masks at stride 4. The host code only reads the ten output tensors.

3 · DECODING

Output decoding

Summary Cells with class score above the confidence threshold become box proposals. Each box side is the expected value of a 16-bin distribution (DFL), measured from the cell centre. Non-maximum suppression removes duplicates. Each surviving detection's 32 coefficients weight the prototype masks; the result is thresholded, mapped back to the frame and clipped to the box.

3a · Score threshold

A cell is a proposal if its class score exceeds conf = 0.5. The HEF already applies the sigmoid, so the scores are probabilities in [0, 1]. In this frame 23 cells pass.

3b · Box regression (Distribution Focal Loss)

For each of the four sides, the cell predicts a discrete distribution over distances of 0…15 grid cells. The decoder applies a softmax over the 16 logits and takes the expected value d. The box edges follow from the cell centre (i + 0.5, j + 0.5) and the stride, then the letterbox transform is inverted:

x1 = ((i + 0.5 − d_left) · stride − pad_x) / s x2 = ((i + 0.5 + d_right) · stride − pad_x) / s y1 = ((j + 0.5 − d_top) · stride − pad_y) / s y2 = ((j + 0.5 + d_bottom) · stride − pad_y) / s

3c · Non-maximum suppression

Neighbouring cells propose nearly identical boxes. cv2.dnn.NMSBoxes keeps the highest-scoring box and removes every box whose IoU with it exceeds 0.45. The function expects (x, y, w, h); the boxes are converted from corner format before the call. In this frame 23 proposals reduce to 3 detections: twig (0.97), stick (0.93), ceiling beam (0.61).

3d · Mask assembly

  1. Linear combination of the 32 prototypes (160×160) with the detection's coefficients, then a sigmoid.
  2. Crop to the image band of the letterbox (prototype rows 35–124, i.e. input rows 140–499).
  3. Bilinear resize to 1280×720 and threshold at 0.5.
  4. Clip to the detection box.

The prototype resolution is the limiting factor for thin branches: one prototype cell corresponds to 8×8 frame pixels. §V shows that mask widths exceed the edge-measured width by a factor of about 2.2; the size sent to the controller is therefore measured on the image edges (§6), not on the mask.

4 · TRACKING

Multi-object tracking (ByteTrack)

Detections are independent per frame. ByteTrack (supervision 0.28) associates them over time: a Kalman filter predicts each track's box, and detections are matched to predictions by IoU (Hungarian assignment). The track ID lets the candidate selection stay on the same branch across frames.

Score thresholds

ByteTrack splits the detections of a frame by score. Detections above track_activation_threshold enter the first association and are matched to all tracks. Tracks that remain unmatched are then matched to the detections scoring between 0.1 and the activation threshold (second association, IoU ≥ 0.5). A second-stage detection can only extend an existing track. A new track requires an unmatched first-stage detection with a score of at least the activation threshold + 0.1; unmatched low-score detections are discarded.

With the installed values (detector 0.5, activation 0.25) every detection enters the first stage, and the second stage never receives a detection. The tested configuration (§V4) lowers the detector threshold to 0.15 and raises the activation threshold to 0.5. Detections scoring 0.15–0.5, typical of motion-blurred frames, can then keep an existing branch track alive but cannot create one; a new track needs a score of 0.6.

After tracking, only the masks of tracked detections are kept. The best track changes only if another track scores at least 0.05 higher (§5d).

5 · POST-PROCESSING

From masks to a perch point

PostProcessor runs five stages in order on the shared context: MaskExtraction → DistanceHeatmap → BitmaskSkeleton → CandidateScoring → CandidateVisualizer.

PostProcessor L7–11 stage order L118–121

5a · MaskExtraction

The union of all track masks gives binary_mask (uint8, 0/255). The per-track masks remain attached to their tracks for the candidate selection.

5b · DistanceHeatmap

cv2.distanceTransform (L2, 5×5 mask) assigns each foreground pixel its Euclidean distance to the nearest background pixel. On the medial axis this is the local half-width. The map is normalised to [0, 1] for scoring; its maximum, heatmap_max_px (19 px in this frame), is stored so normalised values can be converted back to pixels.

5c · BitmaskSkeleton

skimage.morphology.skeletonize reduces each foreground region to its one-pixel-wide medial axis. Perch points are restricted to skeleton pixels, so every point lies on a branch centreline. Skeleton pixels with exactly one 8-neighbour are end points; pixels with three or more neighbours are junctions (forks, crossings).

5d · CandidateScoring

Summary Per track: an orientation test, then the skeleton pixels inside the track's own mask are filtered by an end-point rule and a crossing rule; the remaining pixel with the highest thickness/centrality score becomes the track's candidate. Tracks are ranked by a weighted score with hysteresis on the previous winner.
  • Orientation. A line is fitted (cv2.fitLine, L2) to the track's skeleton pixels, or to its mask pixels if fewer than 10 skeleton pixels exist. With VERTICAL_ONLY, a track is a candidate only if its axis is within 30° of the image vertical; tracks whose orientation cannot be determined are rejected. The rule reflects the operating procedure: the pilot yaws the UAV so that the target branch appears vertical. Rejected tracks still count as obstacles for the crossing rule.
  • End-point rule. A candidate pixel must be at least 30 px from every skeleton end point, and at least max(30 px, 5 widths) + half a width from the branch's two tips (the farthest-apart end points, excluding ends within 3 px of the frame border, where the branch leaves the image). If no pixel remains, the track yields no candidate (NO_ROOM). Motivation: the width cannot be measured at a tip (2026-10-13 10:19: lock on a stub tip, size in 12% of packets).
  • Crossing rule. Blocked pixels: other tracks' masks, skeleton junctions, bulges (half-width above 1.6 × the track median), and pixels where the background on both sides (sampled 6 half-widths + 4 px from the axis) is at least 25 grey levels darker than the track's typical background, which detects unsegmented wires and pipes. Candidates must keep a clearance of max(10 median half-widths, 15 px), i.e. five branch widths, from blocked pixels; if this removes every pixel, the rule is skipped.
  • Pixel score. 0.6 · thickness (distance transform normalised within the track) + 0.4 · centrality (1 − distance to the image centre / half-diagonal). Ties resolve in raster order, so identical input gives identical output.
  • Hysteresis. The previous frame's point is kept if a valid pixel lies within 60 px of it and scores at most 0.3 below the best pixel.
  • Track score. sigmoid(2 · (0.4 · confidence + 0.35 · thickness + 0.25 · centrality)). The previous winner remains selected unless another track exceeds it by 0.05. The candidate also carries distance_to_boundary, the half-width at the point in pixels.

6 · HAND-OFF

Hand-off to the IBVS tracker

The detection loop yields the frame, the selected candidate, the mask of its track, the union mask of all tracks and the grab timestamp. DetectionPipelineSource converts this into a point and an initial width estimate (2 · distance_to_boundary). IBVSPipeline (ibvs repository) locks only if the point is at least 50 px inside the image and the edge-based width measurement (BranchWidthTracker) succeeds at the point on two frames; it prefers points away from crossings. After the lock, the point is tracked with KLT and the detector idles until the target is lost.

7 · SIZE

Branch width measurement (packet size)

In branch mode the UDP packet carries, besides the perch point (px, py), the apparent width of the branch at that point in pixels (size) and the time from frame grab to transmission (age). The UAV uses the size only to estimate the time to contact (TTC) during the climb. It fits a least-squares line to ln(size) over the last second, and the slope is the expansion rate. The estimate therefore depends on the frame-to-frame ratio of the size, not on its absolute value: a constant scale error cancels, while noise of a few per cent between frames enters the slope directly.

packet {"px": 603, "py": 474, "size": 25.31, "age": 0.0629} 2026-10-14 12:00, frame 1410 rate = d ln(size) / dt least squares over 1 s, at least 10 samples TTC = 1 / rate distance = v_climb · TTC − v_climb · 0.5 s (the fit describes the middle of the window) STRIKE when distance < strike_distance (0.30 m) and the point is aligned, held for strike_confirm_s

size and age are omitted from a packet when they are not valid; they are never sent as 0 or null. age is measured on the Pi's clock and sent only when it is below 1 s.

Why the mask is not used

The detector does not run while KLT tracks the point, so no mask exists on most frames. The mask is also too coarse: one prototype-mask cell is 8 × 4.5 px in the frame, about 10 % of a 20 px branch. The mask is used once, at the lock, to initialise the measurement. From then on BranchWidthTracker (ibvs repository) measures the width on the image edges on every frame.

Measurement

  1. Initialisation at the lock. From the mask in a window of ±max(3w, 40) px around the point: the branch direction (principal axis of the mask pixels), the polarity (branch darker or brighter than its surroundings) and an initial width (2 · distance to the mask boundary, from the detector). Before the lock the same measurement runs at the detection; the lock requires two agreeing frames (§6). If no width is obtained for 8 detection frames, spots along the branch at ±1, 2, 3, 4 and 6 widths are tried, nearest first.
  2. Cross-sections. 17 intensity profiles perpendicular to the branch, centred on the tracked point and spaced clip(w/4, 3, 10) px along it. Each profile is ±(1.5w + 6) px long, sampled every 0.5 px by bilinear interpolation of the grey image and smoothed with a Gaussian of σ = 1 px. Samples within 3 px of the image border are not used.
  3. Background crossings. Where a wire or beam crosses behind the branch, the background on both sides is darker than the plain background by at least 40 % of the branch contrast. Those cross-sections, with a 2 px margin, are excluded unless fewer than 8 would remain.
  4. Edges. On each profile the strongest falls of the gradient (entering the branch) and rises (leaving it) are paired. The pair kept is the one whose distance is closest to the expected width and whose centre is closest to the point; the ratio to the expected width must lie in 0.4–2.5 (0.2–3.0 before the first confirmed width). Each edge is then placed with sub-pixel precision where the profile crosses the level half-way between the branch interior and the background beside that edge. Both sides need a contrast of at least 6 grey levels.
  5. Aggregation. At least 8 of the 17 cross-sections must yield both edges. The width is the mean of the middle half of the sorted widths. The branch direction is re-estimated from the cross-section centres, and the width is corrected by the cosine of the direction error, since a cross-section that is not perpendicular to the branch measures w / cos α.
  6. Acceptance. The cross-sections must agree (median absolute deviation at most 20 % of the median width), and the width must be at least 3 px. It must also lie within a factor 1.3k of the last accepted width, with k = 1 + (frames since the last accepted width) / 10. After a lock or a re-find, the first width is sent only when two consecutive frames agree within 15 %.
  7. Recovery. After 3 failed frames in a row, the direction is re-estimated from the structure tensor of the image gradient around the point when it differs by more than 10°. The expected width is re-measured from one wide profile when it differs by more than a factor 1.3. Near a branch end, where edges are found on one side of the window only, the window moves that way by a quarter of its length per frame, up to half of it.

If a condition fails, the packet is sent without size, and the reason appears on the [size] line of the flight log (for example "edges found on only 6/17 cross-sections" or "width jumped 8.1 -> 12.4px"). An accepted measurement also moves the tracked point sideways onto the branch centreline (median of the cross-section centres) when the offset is at most one width. In the 2026-10-12 flights, at 6–8 px (branch far away), the width varied by about 2 % from frame to frame and by about 3 % around its 1 s trend.

Limitations

  • The TTC in the overlay is reconstructed from the sent packets with grab timestamps. The UAV computes it from its receive times and publishes its own values (size, TTC, distance) on ibvs/closeness; the two can differ by the network jitter.
  • The video is written at the frame rate of the raw recording, which is measured over its first frames. In the 12:00 run this gave 13.8 fps, while the loop averaged 19.5 Hz (1504 frames in 77.2 s), so the video plays at 0.71 × real time. Durations should be taken from the stamp or the JSON file.
  • The status panel, the size graph and the stamp are redrawn every third frame to save render time, so their numbers can lag by up to two frames. Point, reticle, cross-sections and features are drawn on every frame.

Validation on recorded flights

Three offline tests on the raw videos of the 2026-10-12/13 flights, run on the Pi with the Hailo-8. Frames: every 40th frame of 33 videos (746 frames). No ground-truth labels exist; the measures are detection and candidate availability, confidence, and the mask width compared with the width measured on the image edges (BranchWidthTracker, sub-pixel).

I · ISSUES AND CHANGES

Issues and changes

Status of the issues found in the code review and the offline tests. The fixed items were committed on 2026-10-14 (detection_pipeline 9bc1357).

Skeleton neighbour count: end-point rule and junction blocking inactive fixed

CandidateScoring counts skeleton neighbours with cv2.filter2D and a uint8 kernel. With OpenCV 4.10 this returns wrong sums (1 along a line instead of 3), so _endpoints found almost no end points and no pixel reached the junction threshold. Consequence: the end-point rule (30 px from ends, five widths from tips) and the junction part of the crossing rule were largely inactive in all flights. Change: float32 kernel. Measured on 606 recorded frames: as flown, 25 % of the candidates were closer to a branch tip than the intended 5.5 widths (12 % closer than 3 widths); with the change, 0 %.

CandidateScoring.py (as flown)

Box anchor at the cell corner instead of the cell centre fixed

YOLOv8 regresses the box sides from the cell centre (i + 0.5, j + 0.5). The decoder used the corner, shifting every box up and left by half a cell (up to 32 px in x and 18 px in y at 1280×720). Masks are clipped to their box, so the right and lower parts of the branches were cut off (median 20 % of the mask pixels).

HailoSegDetector.py (as flown)

NMS received corner coordinates fixed

cv2.dnn.NMSBoxes expects (x, y, w, h); it received (x1, y1, x2, y2), which inflates the boxes and can merge adjacent detections. Effect in the recordings: 1 % of frames.

HailoSegDetector.py (as flown)

Squashed input instead of letterbox fixed

Resizing 1280×720 to 640×640 distorts the aspect ratio by a factor of 1.78. The letterboxed input raises the detection confidence and the share of frames with a candidate (§V1), consistent with letterboxed training data.

HailoSegDetector.py (as flown)

Ceiling beam detected as a branch resolved

The network detects the horizontal ceiling beam (confidence 0.59–0.61). Under the previous orientation rule (horizontal or vertical) it was a valid candidate and nearly won (0.834 vs 0.840). The vertical-only rule (±30°) rejects it; its mask still acts as an obstacle for the crossing rule.

Detector confidence threshold decision

In a visual check of 24 random detections with confidence 0.5–0.7, 23 were the target branch (often a partial segment) and one was a false positive. With the squashed input a threshold of 0.8 would remove a quarter of the candidates; with the letterbox the loss is 8 percentage points (§V1). With the vertical-only rule there is no known false positive that a higher threshold would remove. The opposite direction, a detector threshold of 0.15 with ByteTrack activation 0.5, was tested in replay (§V4): twice as many searching frames with a detection, an earlier lock in the vibration-heavy 16:11 run, +0.8 ms per detection frame; not installed.

ByteTrack low-score association unused info

With the detector threshold (0.5) above track_activation_threshold (0.25), the second association stage never receives detections. A detector threshold below the activation threshold enables it (§4); the configuration 0.15 / 0.5 is evaluated in §V4.

Debug image rendered in the flight loop open

CandidateVisualizer runs on every detection frame and costs about 10 ms (6 % of a detection frame). The image is only used for the recording; it could be rendered in the recorder's background thread or after the flight, as is already done for the main overlay.

Automatic exposure and focus open

Motion blur is the main cause of tracking losses (loss probability rises from 0.7 % below 10°/s to 40 % at 60–90°/s body rate). A fixed short exposure would reduce it.

Maintenance info

supervision marks its ByteTrack as deprecated (removal in 0.30). Not used on the UAV: LineFit.py, TrackCoaster.py, the Ultralytics PC detectors and HailoDetector.py (box-only model).
